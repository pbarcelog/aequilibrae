## Context

AequilibraE already creates `public_transport.sqlite` for every loaded project and has GTFS-derived transit service
tables for agencies, stops, routes, route links, pattern mappings, trips, and trip schedules. `Transit.create_graph()`
then derives assignment-ready transit graph nodes and links from those service tables.

The completed VISUM SQLite private-network import intentionally deferred public-transport objects. The Karlsruhe source
SQLite shows that this deferred data is substantial: `STOP`, `STOPAREA`, `STOPPOINT`, `LINE`, `LINEROUTE`,
`LINEROUTEITEM`, `TIMEPROFILE`, `TIMEPROFILEITEM`, `VEHJOURNEY`, `VEHJOURNEYSECTION`, `OPERATOR`, calendar, fare, and
blocking tables are present and populated. The imported Karlsruhe project also preserves `visum_node_no`,
`visum_link_no`, and `visum_zone_no`, which can bridge VISUM line-route records to AequilibraE network records.

The importer must respect existing transit table contracts and SpatiaLite geometry handling. It should populate service
tables first and rely on existing transit graph construction for assignment graph generation.

## Goals / Non-Goals

**Goals:**

- Add a VISUM SQLite transit import workflow for projects whose private network has already been imported from the same
  VISUM SQLite source or otherwise preserves compatible VISUM source-reference columns.
- Populate `public_transport.sqlite` service tables for operators/agencies, stop points, line-route patterns, route
  links, pattern-to-network mappings, trips, and stop schedules.
- Convert VISUM time-profile offsets and vehicle journey departures into AequilibraE integer seconds from midnight.
- Map VISUM `BUS`, `TRAM`, and `TRAIN` systems to AequilibraE route types and default PCE/capacity values with
  configurable overrides.
- Provide diagnostics for missing source tables, unmapped transit systems, missing source-reference joins, partial
  vehicle journeys, deferred VISUM tables, and imported row counts.
- Validate that imported VISUM transit service data can build a transit graph and preload vector for a representative
  time window.

**Non-Goals:**

- Convert VISUM public transport data to GTFS files as an intermediate import path.
- Import fare computation, detailed ticket rules, vehicle blocking/coupling, depot operations, or vehicle unit rosters.
- Implement multi-service-calendar behavior beyond the source calendar/valid-day subset that can be represented by the
  current AequilibraE transit tables.
- Change transit assignment algorithms, hyperpath behavior, Cython kernels, or result persistence.
- Rebuild or mutate the private-traffic network as part of transit import.

## Decisions

### Use a transit gateway entry point

Add the primary user workflow under the transit gateway, for example `Project.transit.import_from_visum_sqlite(...)` or
an equivalent public `Transit` method. This keeps the VISUM transit import aligned with existing public-transport
workflows such as `Transit.new_gtfs_builder(...)`.

Alternative considered: extend `Project.network.create_from_visum_sqlite(...)` with an `import_transit` flag. This is
convenient for all-in-one imports, but it couples a private-network constructor to transit service-table side effects.
A convenience flag can be added later if the explicit transit workflow proves too verbose.

### Populate service tables, not generated transit graph tables

The importer should write `agencies`, `stops`, `routes`, `route_links`, `pattern_mapping`, `trips`, and
`trips_schedule`. It should not directly populate transit `nodes` or `links`; those are generated by
`Transit.create_graph()` for a requested period and graph configuration.

Alternative considered: directly translate VISUM line-route items into transit graph nodes and links. This would bypass
existing graph-builder logic and risk diverging from GTFS-based transit assignment behavior.

### Require source-reference joins to the imported network

VISUM line-route items and stop points reference VISUM node, link, and stop-point identifiers. The importer should join
those references to AequilibraE network records through preserved columns such as `visum_node_no`, `visum_link_no`, and
`visum_zone_no`. If those columns are missing or insufficient, the importer should fail before writing service data or
report that the project network is not compatible with VISUM transit import.

Alternative considered: spatially snap VISUM stops and line routes onto the AequilibraE network. The Karlsruhe source has
complete identifier coverage, and deterministic source-ID joins are more faithful and easier to validate than geometric
snapping.

### Treat VISUM line route plus time profile as an AequilibraE pattern

VISUM `LINE` identifies the public transport line, `LINEROUTE` gives direction-specific route variants, and
`TIMEPROFILE`/`TIMEPROFILEITEM` define stop sequences and relative timings. Each importable line-route/time-profile
combination should become a route pattern in `routes`, with stop-to-stop entries in `route_links` and source network
link entries in `pattern_mapping`.

Alternative considered: collapse all time profiles for the same line route into one pattern. This loses cases where
time profiles have different stop ranges or timing points and makes partial vehicle journeys harder to represent.

### Build trip schedules from vehicle journey spans

VISUM `VEHJOURNEY` records provide actual departures and reference a line route, time profile, and from/to time-profile
item span. The importer should combine the journey departure with `TIMEPROFILEITEM.ARR`/`DEP` offsets, trim the sequence
to `FROMTPROFITEMINDEX` through `TOTPROFITEMINDEX`, and write integer arrival/departure seconds to `trips_schedule`.
Trips that cross midnight should retain monotonic seconds, even when values exceed 24 hours.

Alternative considered: import only headways from `TIMEPROFILE.HEADWAY(AP)`. The source contains explicit vehicle
journeys, and AequilibraE preload and graph-building logic already expects concrete trip schedules.

### Defer unsupported VISUM public transport features explicitly

Fare systems, transfer-walk-time semantics, block versions, vehicle coupling, depot fields, and detailed calendars
should be recognized in diagnostics but not partially imported unless they can be represented without changing the
current transit schema.

Alternative considered: add new transit schema columns for every VISUM PT concept immediately. This would increase
migration and documentation risk before the core stop/route/timetable import path is proven.

## Risks / Trade-offs

- VISUM time fields may include values beyond simple `HH:MM:SS` or implicit day rollovers -> Centralize time parsing and
  add tests for midnight and partial-journey cases.
- Current transit tables are GTFS-shaped and may not preserve every VISUM identifier -> Add diagnostics and, if needed,
  limited provenance columns only after confirming existing fields are insufficient.
- `pattern_mapping` foreign-key behavior is imperfect in the current schema -> Use existing insertion patterns and test
  graph/preload behavior rather than relying only on constraints.
- Large VISUM models can produce many route-item and trip-schedule rows -> Use set-based SQL/pandas transforms and batch
  inserts; avoid per-row SpatiaLite geometry calls where bulk WKB inserts are possible.
- Importing into a non-empty `public_transport.sqlite` can create duplicate routes or stale graphs -> Require an
  explicit overwrite/append policy and remove saved transit graphs when service tables are overwritten.
- The source network may not have been imported from the same VISUM SQLite file -> Validate source-reference coverage
  before writes and report coverage counts.

## Migration Plan

No schema migration is expected for the first implementation if existing transit service tables are sufficient. If
durable VISUM provenance columns become necessary, add transit schema files/migrations and tests before importer writes
depend on them.

The importer should run inside a transaction on `public_transport.sqlite`. On overwrite, it should clear existing
service data in dependency order and remove saved transit graph records for affected periods before inserting new
service data. A failed import should roll back transit table changes and leave the private-network database untouched.

## Open Questions

- Should the final public method name be `import_from_visum_sqlite` or `create_from_visum_sqlite` on the `Transit`
  gateway?
- Should default VISUM transit-system mappings be fixed to `TRAM=0`, `TRAIN=2`, `BUS=3`, or loaded from project
  parameters?
- Should imported VISUM stop identifiers use `STOPPOINT.NO`, `STOP.NO`, or a composite identifier when multiple stop
  points belong to the same stop area?
- Should the first implementation support append mode, or require overwrite-only imports until duplicate handling is
  specified?
